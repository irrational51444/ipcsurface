## 「只有粗扫」的 22 条，三条来源

### 一、二进制文件里的字符串（抖音 10 条）

`cancel-to-update`、`quit-and-install-update`、`openFolder`、`REPORT_STAT`、
`__CANS_MAIN_STATIC_SETTING__`、`maximize`、`minimize`、`close` 这些。

粗扫把 asar 里**所有文件**当文本扫，包括 `.node` 原生模块、`.exe`、`.dll`。
这些字符串确实在文件里，但它们躺在二进制的符号表和资源段里，
不在任何 JS 注册点上。

精扫只扫 `.js` / `.mjs` / `.cjs`，看不见这些——**这是对的**。
二进制里出现一个字符串，不构成「这里注册了一条 IPC 通道」的证据。

这条要记住：粗扫的通道数里混着二进制噪音，数字偏大不是因为它看得多。

### 二、渲染层的调用点，不是主进程的注册点（ASUS 2 条、vivo 1 条）

`devicePage`（ASUS）、`online`（vivo）都在渲染层/preload 里被 `ipcRenderer` 调用过，
但主进程那份 asar 里找不到对应的 `ipcMain.*` 注册。

粗扫的 `channels` 是 **handler ∪ invoke** 的并集，两边都算；
精扫只数注册点。两个口径不同，不是漏。

真要回答「渲染层喊了但没人接」这种问题，得两边都留着比对——
现在报告里 `handlers` 和 `invokes` 是分开列的，可以自己比。

### 三、ACLOS 那 9 条

`did-finish-load`、`did-fail-load`、`did-attach-webview` 这类是 **webContents 事件名**，
不是 ipc 通道；还有一条是 shell 命令串被当成了名字，一条是字面量 `undefined`。
精扫按「ipcMain 注册点」取，天然不会收这些。

## 精扫这边真正的收获

### ASUS：3 条从「未判定」变「确认干净」

```
ipcMain.on("uwp", this.onUWPEvent)
```

ES5 原型写法，方法体在 `e.prototype.onUWPEvent = function () {...}` 里。
早先只收 `class X { m() {} }`，这三条只能判 `unresolved`。
补上原型方法之后，三个 handler 都追到了，里面确实没有危险调用。

覆盖率 0% → 100%。

### 抖音：13 条，9 条走常量表

`const-table` 9 / `literal` 4。全是 `no_sink`。
抖音的通道名大半是从常量对象里取的，不查表就只能拿到属性名。

### vivo 手机助手：23 条，全是字面量

全部 `no_sink`。这个包写得最直白。

## 四个 0 通道的包

QQNT、抖音 tray、抖音 widget、VS Code 的 `node_modules.asar`、daziya 客户端——
粗扫和精扫**都是 0**。

QQNT 的 `application.asar` 只有渲染层，主进程在 `QQ.exe` 那一侧；
VS Code 的 `node_modules.asar` 是依赖不是入口；daziya 的 195 MB 里也没有主进程注册点。

这些不是「精扫看不见」，是**两个引擎都没看见**。
`--engine auto` 遇到这种情况会退回名称级并在报告第一屏写明原因。

## 还欠着的

- 这几个 0 通道的包，**没有证明**它们真的没有通道。只能说这两条路都没走到。
  要定论得上运行时探针。
- 抖音和 vivo 的「确认干净」只到「handler 里没有危险 API」这一层，
  没有做污点传播和参数可控性分析。
- 语料只有 Windows 上装的这些，没有 macOS/Linux 侧的应用。
