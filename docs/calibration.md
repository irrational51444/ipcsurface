# 校准：把「能信多少」拆成两层验

路线图 P2-9。`scripts/calibration.py` 拿人工核对的标准答案，验「可信度」指标
是不是名实相符。第一刀发现 strength 档位混了两个问题；第二刀拆成两层。

## 结论先说

「能信多少」不是一个数，是两层，得分开验：

- **名字层**（通道名真不真）——现在**不能校准**，缺假名样本。
- **sink 层**（危险 API 对不对）——**能校准，且单调成立**：路径越可信，精确率越高。

## 表一：名字层（暂不能校准，是缺样本，不是跳过）

人工确认过的通道名 50 条，其中 23 条（抖音 22、bilibili 1）只确认了名字真、
sink 读不到，不参与表二。

| strength 档 | 通道名数 |
| --- | --- |
| 1.0 | 24 |
| 0.9 | 3 |

名字层校准需要两个样本，golden 都没有：

1. **精确率要「假通道名」样本**——工具瞎编的名字。golden 里人工读到的名字全是
   真的，没有假名，所以「strength 高 = 名字更可能是真的」这个命题验不了。
2. **召回率不能拿 golden 算**——人工只核「工具报出的」名字，所以
   「报出的 / 确认过的」必然是 100%，这是循环论证，不代表不漏。

真正的不漏要拿运行时探针对齐（P1-8 `probe_align`，实测 71% 对齐）。

## 表二：sink 层（能校准，单调成立）

通道名对的前提下，报出来的危险 API 对不对。用「sink 路径强度」分档。

**两个口径，别看混**：

- **API 级**：一个通道报了 9 个 API 误报就算 9 次。会被「一个大包」放大——
  vivo 一个包的 9 条误报通道就报了 77 个 API，把 ast_only 从 25% 拖到 1%。
- **通道级**：一条通道在同一档最多算 1 次。**基线比对这个口径**——
  问的是「这条通道该不该信」，不是「它顺手报了几个 API」。

2026-11-12 实测（6 个包，117 条人工确认通道名）：

| sink 路径档 | API 对 | API 误报 | 精确率 | 通道对 | 通道误报 | 通道精确率 |
| --- | --- | --- | --- | --- | --- | --- |
| direct | 2 | 0 | 100% | 2 | 0 | 100% |
| name_confirmed | 5 | 0 | 100% | 5 | 0 | 100% |
| chain | 11 | 0 | 100% | 11 | 0 | 100% |

**结论层 18 条，全对，误报 0。**

## 软档为什么不再产出结论（0.97.0 起）

真踩过的铁证：obsidian 的 `sandbox`（真阳性）和 `set-menu`（误报）报出来的 API
**一字不差**——`existsSync, mkdirSync, readFileSync, readdirSync, rmSync, rmdirSync,
writeFileSync`，七个，顺序都一样。

说明 `ambiguous` / `ast_only` 这两档**根本没在区分通道**，它把同一段代码一起算给了
所有通道。真假通道拿到同一批结论，那就不叫证据。

所以这两档现在：

- **不产出「能碰到什么」**，改写成「这条通道认出来了，它能碰到什么没分析」
- 数据挪进 `channel_sinks_borrowed`，和结论分开
- 校准里单独统计过滤量：**砍掉 87 个误报、9 个真阳性**

那 9 个「真阳性」也一并砍了。它们的「对」是碰巧——工具给出的证据和假通道一样，
留着就是拿巧合当证据。

**取舍写在这儿**：重放的代价是召回掉了 9 条。但一个报 114 条错 87 条的工具
没人敢用；而现在这 18 条，人可以直接信，不用复核算术。

`scripts/calibration.py` 里有一条单调性断言：档位从高到低，精确率不许「越可信
越不准」（倒挂容忍 ≤10%）。现在这条断言是绿的——**路径可信度这个指标，真的能
把「更可能错的 API」分出来**。

这条梯度正是 `docs/benchmark.md` 里「API 精确率 24%」的结构化拆解：24% 不是
均匀地错，而是集中在 ambiguous（同名多义借来）和 ast_only（仅语法树借来）两档。
直连、双口径证实、同文件链三档一个没错。

## 校准进基线（`--baseline`）

```bash
python scripts/calibration.py --write-baseline tests/golden/calibration.json   # 确认没退化时写
python scripts/calibration.py --baseline tests/golden/calibration.json          # 比基线，掉 >5% 退 1
```

基线在 `tests/golden/calibration.json`，**比的是通道级精确率**。任何一档掉超过
5 个百分点就退 1——要么代码退化了，要么 golden 的标注变了，两种都得先查清再发版。

**为什么 CI 不跑它**：校准要扫真包（obsidian / dsh / vivo，本机绝对路径），
CI 上没有这些包。所以这一条是「本机门禁」——`verify.sh` 会提示基线存在，
真正跑它得在有真包的机器上。

## sink 路径强度档的定义

在 `scripts/calibration.py::sink_tier`，按一条危险 API 的来路，从高到低：

- **direct**：处理函数自己直接调（hops≤1），且没经过同名多义。
- **name_confirmed**：语法树和名字级双口径都报，但路径没记录（别名/成员调用）。
- **chain**：同文件内经过一层函数链（hops>1），无同名多义。
- **ambiguous**：经过同名多义链（via 带「同名多义」标记，或通道在
  `channel_sinks_ambiguous` 名单）。压缩产物里同名函数，可能跟错身子。
- **ast_only**：只有语法树口径连上，名字级没连上——最可疑。

## 下一步（诚实的）

1. 名字层要能校准，得补**假通道名样本**：把工具报的通道名里「人工判定是假的」
   标进 golden。这是名字层精确率的地基，没有它，strength 档位永远只能排序、不能验。
2. sink 路径强度档已经验证有效，下一步把它落进**主报告**（`channel_sinks` 输出里
   给每条 API 带一个 `sink_tier`），让读报告的人不用再跑校准脚本就能看出
   「这条 API 是直连还是借来的」。
3. ambiguous 档 53% 还是太高：同名多义链里有一半是对的（sandbox 的 rmSync 经 f()、
   adblock 的 readFile/writeFile），一半是错的（set-menu 借来的 7 条）。要再往下钻，
   得区分「同名多义但同文件可达」和「同名多义跨文件借来」——后者才是真正危险的。

## 历史

- 第一刀（`calibration.py` 初版）：strength 档位 vs 对不对，照出「0.9 档 100%
  反而高于 1.0 档 84%」的倒挂——根因是 strength 量「通道名可信度」却拿去和
  「API 对错」混在一张表。
- 第二刀（本版）：拆成名字层 / sink 层两张表，sink 层用路径强度分档，单调成立。
