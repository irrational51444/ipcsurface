# 校准（strength 档位 vs 对不对）

路线图 P2-9。`scripts/calibration.py` 拿人工核对的标准答案，按 evidence 的
`strength` 档位分层，算每档的精确率（对的 / (对的+误报的)）。

## 第一轮校准数据（2026-11-11，Obsidian + DeepSeek Harness）

| strength 档 | 对 | 误报 | 精确率 |
| --- | --- | --- | --- |
| 1.0（逐字写死） | 21 | 4 | 84% |
| 0.9（还原/穷举证明） | 3 | 0 | 100% |

## 结论：发现一个「名不副实」的地方（这是好事）

`scripts/calibration.py` 会红，因为 **0.9 档的精确率（100%）反而高于 1.0 档（84%）**。

这不是 bug，是一个真实的事实被照出来了：

- **strength 档位量的是「通道名」的可信度**——这个名字是不是真的、写死还是还原的；
- **benchmark 里的误报是「危险 API」层面的错**——通道名没错（都是逐字写死，1.0），
  错的是它后面跟的那个危险 API（同名多义 `f`/`kt`、共用函数 `_`/`ae` 借过去的）。

把「通道名的可信度」和「危险 API 的对错」混在一张表里，就会出这种倒挂：
名字越「写死」，越容易连上一条借来的、其实不归它的危险 API 链。

## 下一步（诚实的）

- 要么把校准拆成两层：**名字层**（strength 档位本来就该管这个，倒挂会消失）和
  **sink 层**（这是 API 精确率 24% 那件事，另立一张表）；
- 要么给 sink 也上一套强度档位（跨文件/共用函数借来的算低一档），再校准。

这正好和 `docs/benchmark.md` 里「API 级精确率 24%」是同一件事的两面：通道名认得好，
危险 API 这条链还没校准。
