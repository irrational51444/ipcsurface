# 已知会错的地方

这个工具是一条路，不是全部。下面这些是我**明确知道**会出错或看不见的情况，写在这里比藏在代码里有用。

## 外部有效性：这些数字能证明到哪一步

「四个靶场 23 条通道、覆盖率 1.00」这个数字是真的，但它只说明**那几个靶场里我没漏**，
不说明这个工具在真实应用上同样靠谱。把话说完整：

| 能证明 | 不能证明 |
| --- | --- |
| 在自造靶场上，支持的那些写法我能认全，且没有误报 | 真实应用里各种构建链、混淆方式下还认不认全 |
| 四个真包（Obsidian / DeepSeek Harness / 抖音 / bilibili）上跑得出结果，注册点解析到 47/47 | 这些结果的人工核对只覆盖 11 条通道，其余是「看见了但没核」 |
| 语法树的未知节点率可以按包量化（0.95%–6.48%） | 未知率低 ≠ 覆盖全：未实现的语法（`@` 装饰器、JSX）会静默丢 |
| 跨文件一跳两跳能跟 | 动态注册、运行时拼名字、跨三个文件以上的间接调用会漏 |

**下一步（按投入产出排）**：

1. 选 3–5 个不同类型的真实 Electron 应用（不只是聊天/编辑器，还要有游戏客户端、工具类），
   每个建独立人工标注集（通道 + 是否真能碰到危险 API），算 precision/recall；
2. 把「人工核对过的通道」数量从 11 条提到每包 20 条以上，并写进 `tests/golden/real_packages.json`；
3. 用运行时探针在其中一个真应用上抓一遍真实注册名，和静态结果对齐——这是唯一能证明
   「动态注册没漏光」的办法。

这三件事没做完之前，README 里那句「不是作者本机那个 441 MB 的应用」旁边的数字，
只能当**「我测过这些」**读，不能当**「这类应用都这样」**读。

### 第一批真实样本上的精确率 / 召回率（2026-11-10）

人工逐条读源码后的账，写在这儿，省得被当成「覆盖率 1.00」那样读：

| 指标 | 数 | 说明 |
| --- | --- | --- |
| 已人工核对通道 | **23 条**（Obsidian 21 / DeepSeek Harness 3，其中 1 条重叠） | 每条都读过源码，依据写在 `tests/golden/real_packages.json` |
| 工具报出（Obsidian，树口径） | 24 条 | |
| 完全对 | 20 条 | 通道 + 危险 API 都对得上 |
| 部分错 | 1 条 | `copy-asar`：`copyFileSync` 对，多报了一个 `exec` |
| 整条误报 | 3 条 | `help`、`starter`（只新建/聚焦窗口）、`set-menu`（只建菜单，却报了一串文件操作） |
| 通道级精确率 | **20/24 ≈ 83%** | 误报来源见下 |
| 已核通道召回 | **23/23** | 核对过的都报出来了；`register-cli` 的 `exec` 是树口径已知漏报（粗扫能抓） |

误报的三个来源，一条条记着：

1. **同名多义**：压缩产物里 `f`、`kt`、`y` 遍地重名。报告会标 `（同名多义）`，
   但一旦选错身子，就会凭空多出几项文件操作（`set-menu` 就是这么错的）。
2. **共用函数**：`_()`/`ae()`（存配置）、`se()`/`ee()`（读配置）、`H()`（打开路径）
   被几十条通道共用，于是很多东西一起被标上「能写文件」。这不算错——
   但它说的是「能碰到」，不是「这条通道会滥用」。
3. **把非 IPC 调用当通道**：这一版已确认 `open-url` 是**真有** `ipcMain.on("open-url")`，
   早先被我误判成 app 事件，现已改成已核。`help`/`starter` 的问题在别处：
   它们只调建窗函数，却被共用链带上。

`register-cli` 那个漏报的根因也说清楚：`let i=(0,ho.promisify)(co.exec)` 里的别名
藏在逗号表达式里，语法树这条链没连上；名字级粗扫能报出来。

## 解析器语法边界（手写 AST 到底认什么）

`jsast.py` 是手写的递归下降解析器。选型理由和实测数据在 `docs/parser-decision.md`；
这里只列**它认什么、不认什么**——边界写在明处，出事的时候能立刻分清是「没有」还是「没认出来」。

### 认的（会进语法树）

| 结构 | 节点 | 备注 |
| --- | --- | --- |
| 变量声明 `var/let/const` | `Var` | 初值保留，供别名判断用 |
| 函数声明与函数表达式 | `Function` | 记形参名 |
| 箭头函数（含 `async` 箭头） | `Function` | `async (e,v)=>{…}` 认；`async function` 也认 |
| 对象字面量里的方法简写 | `Function` + `kind:'method'` | 成员调用只连到这类方法 |
| 调用 `f()`, 成员调用 `a.b()`, 方括号 `a['b']()` | `Call`/`Member`/`Index` | 三种都算调用边 |
| 别名 `const run = co.exec` / `x = fs.readFileSync` | `Assign`/`Var` 初值 | 只认「右边出现危险名字」这一种形状 |
| `if/else`、`for`/`while`/`do`、`try/catch/finally`、`switch` | 对应节点 | 只用于遍历，不建控制流图 |
| `return`/`throw`、`break`/`continue` | `Return`/`Throw`/`Jump` | 不做路径敏感分析 |
| 三元、二元、一元、`new`、模板串、数组、对象、字面量 | 对应节点 | 模板串里的 `${…}` 会当代码切出来 |
| `import`/`export` 语句 | 不建节点 | 直接跳到分号，跨文件解析不依赖它 |

### 不认的（会变成 `Other` 或被跳过，**不会**让整份分析崩）

| 结构 | 现在的表现 | 影响 |
| --- | --- | --- |
| JSX / TSX | 跳过 | 渲染进程里若是 React 代码，那块看不见 |
| 装饰器 `@dec` | 跳过 | 装饰器里的调用看不见 |
| 类字段初始化器 `field = …` | 部分跳过 | 类里的箭头属性可能漏 |
| 生成器 `function*`、`yield` | `yield` 当一元运算 | 生成器体里的调用可能漏 |
| 标签语句、`with` | 跳过 | 极少见 |
| 对象展开 `{...a}`、数组展开 | 当一元/标点处理 | 展开里的调用可能漏 |
| 带 tag 的模板 `` tpl`…` `` | 只认模板本身 | tag 函数调用看不见 |
| 动态 `import()` | 当普通调用 | 跨文件解析不用它，但会记一个 `import` 调用 |
| 可选链调用 `a?.()` | 目前不建边 | 少认一条调用，不误报 |
| 正则细节（命名组、lookbehind） | 整体当一个 `regex` token | 对本题无影响 |

### 两条保底

1. **软失败**：认不出的字符（真包里有 `…` U+2026）、没闭合的字符串/模板/注释，
   一律记数并跳过，不抛异常。`jsparse.tokenize_with_stats()` 会把它们带回来，
   `scripts/ast_coverage.py` 把「未知节点率」当指标打出来（实测 4.4%–6.5%）。
2. **两列并存**：`channel_sinks`（名字级粗扫）永远在。树口径挂了还有它，
   两列都写「没连到」，不许写成「没有」。

## 看不见的（假阴）

| 症状 | 为什么 | 怎么办 |
| --- | --- | --- |
| 注册点写成 `ipcMain.handle(SOME.IPC_EVENTS.KEY, …)`，KEY 的值在别的文件里 | 名字是三层成员链，静态这一层没解 | 报告里 `channel_unattributed` 会报出这种注册点有多少处、卡在哪一行哪个表达式。**实测**：抖音桌面端 20 处，这 20 处的键名在包里都能找到唯一字面量值——按「包里唯一」这条规则能补，但还没接进清单（接之前得先有测试盯住「多值时不许猜」） |
| `try { … } catch (err) { fs.readFileSync(err.path) }`，抛出去的东西**跨了函数**（helper 里 throw、调用处 catch） | 现在只做**同一层 try/catch** 的有界传播：try 里 throw 的表达式带外部输入，catch 变量才算脏；跨函数、嵌套 try 一律不追 | 跨函数的抛出自己回原文看。边界写在 `jssem.catch_taints` 的注释里，尺子还有一条「抛的是常量不该算脏」盯着不许滥认 |
| `channel = 'a' + ':' + b`，而 `b` 来自配置/返回值/循环累加 | 只认写死的字符串，不跑表达式；取值集合不在源码里就没得穷举 | 跑 `rea analyze-javascript-application` 拿 Evidence；或运行时探针 |
| 从网络/配置读来的名字 | 源码里没有那个字面量 | 运行时看；或人工跟配置 |
| `obj[name]` 这种动态属性 | 名字在运行时才知道 | 运行时探针；或看调用点上下文 |
| 拼装函数里带分支或赋值 | 那种拼法不是「字面量加参数」，穷举会算错，所以整处放弃 | 回原文读那个函数；别指望名字 |
| `require` 拼出来的模块路径 | 同上 | 运行时 trace |
| 只注册在渲染进程、代码被 webpack 拆走的通道 | 包里根本没有那段源码 | 打客户端包，别只看主进程包 |
| 加密/压缩后再 eval 的代码 | 静态看不到 | 动起来再探 |

> 运行时探针这条已经**真跑过**：electron v45 起一个最小应用，四条通道里静态只认得一条（字面量），
> 另外三条（常量对象、拼接、运行时拼的）是探针抓回来的。样本在 	ests/golden/probe_sample.jsonl，
> 用例 	ests/test_probe_convert.py::RealRunTests 盯着「运行时比静态多看见三条」这件事。

## 会误报的（假阳）

| 症状 | 为什么 | 怎么办 |
| --- | --- | --- |
| 长得像通道名的字符串 | `xxx:yyy` 这种形状被当候选捞出来 | 那是「候选」，不是结论；要看 `evidence` 里它属于哪一层 |
| 常量表里查出来的名字 | 表可能被覆盖、字段可能同名不同义 | 只能算「靠还原认出」，不算写死 |
| 注释、文档字符串里的示例 | 会一起扫到 | 用 `--fail-on high` 时留意这类，必要时忽略 |
| 混淆器留下的 `Function` 构造器痕迹 | 报的是「这包被动过」，不是「这里有通道」 | 当线索，别当结论 |

## 别拿它当结论用的场合

- 安全评审：它只说明「能读到哪些名字」，不说明门后逻辑有没有校验。
- 版本对比：`--baseline` 说的是「名字有没有变」，不是「行为有没有变」。
- 打补丁验证：同一个名字换了实现，它看不出来。

## 已知的盲区（工具层）

- Windows 上目录刷盘走 `FlushFileBuffers`，句柄必须带写权限（读权限会被拒）；只读卷和网络盘没实测过，那种情况报 `durable=no` 而不是 `unknown`。
- 只读目录没在真实只读卷上跑过。
- `adv-asar.asar` 是手工对抗样本，仓库里没有生成脚本。

## 交叉档位的已知损失

`weak-near-line`（同文件相隔 1–5 行）里混着两种情况：同一调用点的两种视角，和只是行号相邻的两段无关代码。静态不建语法树就分不出这两者，所以档位名只说「相邻」，`corroboration_basis` 里也明写「分不清」。想再细，得上 REA 的 AST 或人工看那几行。

## 交叉档位的现状

`corroboration_level` 只有**探针给出位置**（probe JSON 里的 `sites`）才算得出来。不催不催：探针只报名字、不报位置时它是 `unknown`——那说明这一档没计算，不说明两条路不独立。

0.80.0 起用真实 CLI 跑过一次带 `sites` 的探针输入（`dyn` 靶场）：`strong`（两个不同文件）、`weak-near-line`（同文件相隔 2 行）、`weak-same-line`（同一行）都真的出现了，不是摆设。`medium` 要同文件相隔 5 行以上才到，`unknown` 就是位置缺失。

## 已知的扫不到（有数字）

`tests/golden/ground_truth.json` 里 `dyn-asar` 那组：`ledger:add/list/remove` 是 `for (const op of OPS) ipcMain.handle(makeChannel(op))` 拼出来的。0.73.0 及以前静态扫不到，记在 `known_unreachable` 里，那组总覆盖率只有 0.50、平均 0.88；0.74.0 起能穷举（`OPS` 是字面量数组、`makeChannel` 是单表达式函数），这一栏空了，平均 1.00。0.80.0 补了三条证明，这三条名字的强度从 0.75 提到 0.9。

**别把 1.00 读成「扫得全」**：四个靶场一共 23 条通道，写法都是我自己写的，代表不了真实应用。真实应用里那 41 条通道，穷举出来的是 0 条。

## 穷举这一档自己的边界

- 强度分两档，按三条检查定：0.9（三条全过）与 0.6（有一条没过）。哪条没过写在 `enum_proof.failed` 里。
- 检查查的是「源码里没有那种写法」，不是「运行时只会取这几个值」：`eval`、`Object.defineProperty`、代理对象这些改写手法都不在检查范围。
- 取值超过 64 个、展开超过 256 个名字，整处放弃，不截断交半份。
- 拼装函数只跟三层，带分支/赋值/循环的不跟。

## 「候选」的准确率（有数字的部分）

`scripts/harvest_precision.py` 用人工标注的靶场算准确率：17 个候选，17 个是真通道名，**1.00**。这几份靶场是我自己写的、样本很小，说明不了真实应用。

真实应用那边只报能机械算的：221 个候选里 41 个同时是静态通道名（不是误报），180 个孤证；其中 12 个出现在提到 IPC 的文件里、0 个紧挨调用、168 个只在别处出现，96 个成簇、84 个零星。**准确率仍然是未知**——没人工核对过，不编。
