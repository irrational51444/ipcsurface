# 术语对照：我说的词，在行业里叫什么

本项目的档位名（`direct` / `chain` / `ambiguous` …）是自己起的。这篇做一张对照表，
让别人一看就知道我在分析链路的哪一层，不用猜。

## 证据档位

| 本项目的词 | 行业里通常叫 | 说清什么 |
| --- | --- | --- |
| `direct` | **intra-procedural**（过程内） | API 调用在一跳以内（`hops ≤ 1`）。**不是「字面就在函数体里」**——处理函数调一次 `ce()`、`ce()` 里再调 `unlinkSync`，这条仍算 `direct`。审 obsidian 时就被这一点绊过，见 `docs/audit-obsidian.md` |
| `chain` | **inter-procedural**（过程间） | 跨过一次以上函数边界，但在同一个文件内跟得到 |
| `name_confirmed` | 双来源确证、未记录路径 | 名字级和语法树两路都报，但爬升路径没记下来 |
| `ambiguous` | **name resolution ambiguity**（名字解析歧义） | 压缩产物里同名函数太多，跟的那一份可能不是对的 |
| `ast_only` | **AST-only / syntax-directed** | 只有语法树看得见，字面量口径完全没报 |

`direct` / `chain` 这两档是标准的分层；`ambiguous` 对应的是**别名分析**（alias analysis）
做不准时的情况——压缩过的 JS 里，`f`、`y`、`m` 满地重名，作用域分析不做就分不清谁是谁。

## 两个不同的问题，别混

这两个词在本项目里分得很开，注释里也写了：

| 问题 | 行业叫法 | 本项目在哪 | 要什么 |
| --- | --- | --- | --- |
| 这条通道**能不能碰到**危险 API | **reachability**（可达性） | `jssem.reachable_sinks` | 只要调用图，实参从哪来不重要 |
| 外部输入**能不能到达**危险参数 | **taint analysis / data-flow**（污点分析） | `jssem.catch_taints`（很浅） | 要参数绑定和数据流 |

**用污点分析去算可达性会怎样**：实测过，会把「自己拼路径再写文件」的通道全判成 0。
两个问题的答案不是一回事，工具不能拿一个冒充另一个。

## 精度和召回怎么算

| 词 | 本项目定义 | 注意 |
| --- | --- | --- |
| 精确率（precision） | 报对的 API 数 / 报出的 API 数 | 分母是「我报了多少」，测量过的 |
| 召回率（recall） | 报对的 API 数 / 该有的 API 数 | **分母从没真测过**——见下 |
| 通道级 vs API 级 | 一条通道在同一档最多算一次 / 每个 API 算一次 | 前者稳定，后者会被大包放大 |

**召回率为什么没测**：人工只核「工具报出来的那些名字」，所以「报出的 / 确认过的」
必然是 100%——这是循环论证，不代表不漏。唯一的外部对照是运行时探针对齐，实测 71%。

这条写在这里，是因为**「召回率 100%」这种话如果出现在别处，那一定是算错了**。

## 不确定怎么标

| 本项目 | 行业里的对应做法 |
| --- | --- |
| 五档来路 | 证据分级（evidence grading）/ 置信分层 |
| 三段证据完整度（`full` / `locate_only` / `name_only`） | provenance completeness |
| `corroboration: none / static_static / static_runtime` | 独立见证（independent corroboration） |
| `severity` + `confidence`（Electronegativity 的标法） | 也是同一件事的另一种表达 |

**同源复核不算独立见证**：两个静态来源共享同一份源码，结果一样只说明「两次错在同一个
地方」。真独立得是静态 vs 运行时。这条在 `docs/calibration.md` 里也写了。

## 为什么值得写这一篇

不是为了显得专业。是因为**自造术语最大的风险是别人看不懂就当你没说**。
把话翻译成行业语言，别人才有办法判断你说得对不对——包括判断你说错了。
