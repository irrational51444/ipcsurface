# ADR：用局部子图查询替代深度遍历（opt-in，增量）

**状态**：第一步已完成，主链路未切换
**日期**：2026-11-14
**决策**：不引 joern / CodeQL，自建「通道相关的局部子图」，在子图上做可达查询。

## 为什么要动

现有 L1–L3 解决的是同一个文件里的数据流。跨文件只能靠 `interproc_taint` 一层层
爬调用栈，而爬的层数必须锁一个上限——实测 depth=3 相对 depth=2 耗时 +67%、
结果零变化，于是锁在 2。

问题不在于深度设得小，在于**遍历模型本身**：沿调用栈爬的时候，跨文件、回调、
循环里的数据流天然爬不全，而任何锁定的深度都同时漏两种东西——

- 链长于上限的（假阴）；
- 链里绕路的（噪音，因为爬的时候不看路径上有没有校验）。

## 谁建图：自建，不引外部引擎

| 路线 | 判定 |
| --- | --- |
| joern（js2cpg） | JVM 依赖 + 对 webpack 压缩产物的建图质量未知，破坏零依赖 |
| CodeQL | 引擎闭源、查询语言受限，且产出受其授权约束 |
| **自建轻量 CFG + def-use** | 唯一不破坏零依赖的路线，产出归自己 |

不引外部引擎的另一个理由是**范围可控**：不需要全局 CPG，只需要「通道相关的子图」——
从 `ipcMain.on/handle` 出发，把它涉及的 handler、被调函数、模块依赖、def-use
收集成局部图。对 obsidian 这是几十个函数，不是 3.9 MB 全量。

## 第一步做了什么（已完成）

`jssem.subgraph_summaries(tokens, defs, roots)`：

1. **轻扫**：只找每个函数体里的调用点，建调用边（不跑数据流）；
2. **重扫**：从 roots 沿边 BFS 拿可达集，只对可达集跑 `flows_into_danger`；
3. **组合**：在可达集内部迭代拼摘要到不动点。

关键点：roots 常常是**内联 handler**，不在 `function_defs` 里，所以 BFS 起点
要从 handler 体内找调用目标，不能拿 handler 自己去查表。

### 验证一：能走多深（合成用例）

五层链 `handler → a → b → c → d → writeFileSync`：

| 做法 | 命中 |
| --- | --- |
| 递归 depth=2 | **0**（漏） |
| 递归 depth=3 | **0**（还是漏） |
| 递归 depth=4 | 1 |
| 子图查询 | **1**（不设深度参数） |

### 验证二：复现现有命中（真包，diff 必须为 0）

| 包 | 老口径通道 | 子图通道 | 文件级 diff |
| --- | --- | --- | --- |
| obsidian | 0 | 0 | **0** |
| ACLOS | 1 | 1 | **0** |

样本薄（真包上 L3 本来就几乎不命中），所以这一轮的证据主要是合成用例。

### 验证三：共用函数不连坐

两个 handler 调不同工具函数，只有碰危险接口的那个被报出来。

## 三个风险（写在这里，不写在事后）

### 1. 压缩产物的 CFG 失真度是最大未知数

webpack 产物一行几十万字符，函数边界靠 tokenizer 恢复，`eval`、动态 require、
字符串拼接模块加载都会让调用边断掉。

**缓解**：先拿 obsidian 的子图做实验，量「边覆盖率」再决定规模，别一上来全局。
现在只做到「调用边」，控制边和数据边还没建。

### 2. 图查询的调试难度比遍历高一档

遍历错了是「少一条」，图错了是「环、误连、爆炸」。

**缓解**：图构建带不变量断言——每个 sink 路径必须有源、每条边两端节点必须存在。
BFS 靠 `visited` 防环，摘要组合按轮数封顶。

### 3. 措辞纪律：图口径不是「确认」

图查询天然像在「下结论」（可达 = 判定）。

**缓解**：图口径产出仍然分层，叫 `graph_confirmed` 而不是 `confirmed`。
`refutes_if` 照写——图的 `refutes_if` 是「这条边可能是假的」，因为压缩产物会断边、
也可能误连。

## 后续阶段（每步用「命中集合 diff 为 0」验证）

1. **补边**（进行中）：模块图加调用边 ✅、数据边（def-use）未做；
2. **统一查询**：AccessPath 可达查询替换 L1–L3，命中集合逐条一致；
3. **sanitizer 节点**：校验函数入图，路径判定分「无拦截 / 有拦截」两档；
4. 深度上限从「锁死的补丁」降级为「粗扫兜底」，图口径成为主口径。

主链路暂时**不切换**：先让 opt-in 路径积累样本，等 diff 在更多包上稳定为 0。

## P0-1：同名多候选边——这是主要路径，不是边角

压缩产物把 `f`、`y`、`m` 复用上百次，`function_defs` 里同名定义一堆。
第一版 `by_name` 只留第一个，等于在猜「调用的是哪一个」。

改成「取离调用点最近的前辈，没有就取最近的后来者」——和 handler 按名字
找函数体用的是同一条启发式。但它是猜，所以单独计数 `edges_ambiguous`。

### 数字（五个真包，`ipcMain` 文件前 40 个）

| 包 | 歧义名 | 确定边 | 猜的边 | 猜的比例 |
| --- | --- | --- | --- | --- |
| obsidian | 12 | 51 | **403** | **89%** |
| aclos | 23 | 38 | **178** | **82%** |
| dsh | 93 | 695 | **2465** | **78%** |
| bilibili | 0 | 0 | 0 | — |
| daziya | 0 | 0 | 0 | — |

**这就是 P0-1 的真实答案：子图上的边，七八成是猜出来的。**

一句话说清它的后果：子图查询在压缩产物上「能走远」，但走的路大多不确定。
合成用例（四层、五层链）里的边全是确定的，所以那些结论不受影响；
真包上的结论要打折——不是「子图多抓了什么」，而是「子图多猜了什么」。

### 五个包的 diff（老口径 vs 子图）

| 包 | 老口径通道 | 子图通道 | 文件级 diff |
| --- | --- | --- | --- |
| obsidian | 0 | 0 | 0 |
| aclos | 1 | 1 | 0 |
| bilibili | 0 | 0 | 0 |
| daziya | 0 | 0 | 0 |
| dsh | 0 | 0 | 0 |

diff 全 0，但通道数本来就几乎为 0——**样本太薄，这一轮证明不了「子图更强」**。
它能证明的是「子图没有把现有结论弄错」。

### 打破这个局面的前提

先让边确定下来。可选方向：

1. 按作用域判可见性（`scope_index` 已有，但要做函数级而不是块级）；
2. 按模块归属判（webpack 模块表里每个模块有独立作用域，同名不冲突）；
3. 只接受「候选之一在调用点所在模块内」的边。

这三条都没做。在它们做完之前，`edges_ambiguous` 这个数字会一直挂在报告里。

## 猜边率：88.8% → 48.5%，根因不是「同名」是「假名」

爸爸把三步的顺序重排了（模块归属优先、作用域次之、顺手加形参个数匹配），
并且要求把猜边率变成可判定的数字。照着做了，结果比预期更值得记：

### 第一个根因：`if`/`for` 被当成了函数名

`function_defs` 认「对象方法简写 `f() {}`」，而 `if (x) { ... }`、`for (...) { ... }`
的形状和它一模一样。于是 obsidian 的 `main.js` 里有 **26 个叫 `if` 的函数定义**、
还有 `for`、`while`……

这些假名字把「同名多候选」抬成了主要路径：候选列表里一堆 `if`，怎么挑都是猜。
过滤掉控制关键字之后：

| 包 | 修前猜边率 | 修后猜边率 |
| --- | --- | --- |
| obsidian | 88.8% | **57.6%** |
| aclos | 82.4% | **39.2%** |
| dsh | 78.0% | **48.3%** |

### 第二个根因：同名函数的形参个数对不上

按「实参个数 == 候选形参个数」粗筛一轮，零成本：

| 包 | 只滤关键字 | 再加形参个数 |
| --- | --- | --- |
| obsidian | 57.6% | **48.5%** |
| aclos | 39.2% | **31.1%** |
| dsh | 48.3% | **41.5%** |

### 模块归属在这一批包上没用上

`module_of` 需要 webpack 模块表。obsidian 的 `main.js` 是单文件打包，`modules=0`，
过滤直接跳过（不能凭空收窄）。所以爸爸预期的「一行过滤砍到个位数」在这批包上
没有生效——不是方法错，是这批包没有模块表。

### 量化判据（写进 ADR，翻案条件要能机器判）

- 模块归属过滤生效后，猜边率 **< 10%**；
- 作用域可见性补完后，猜边率 **< 5%**；
- 两条都达标且五个真包 diff 稳定为 0、新命中人工核过，才允许切主链路。

现在的数字是 48.5% / 31.1% / 41.5%，离 10% 还差一个量级。**P1/P2 继续压着。**

### 同名一律按猜测记账

这条现在写进报告口径：只要一条边的两端涉及同名候选，它就是 `edges_ambiguous`，
不因为「实际挑对了」而洗白。和主链路 ambiguous 档的哲学统一了。

## 把 48.5% 拆开：假名字已经很少，剩下是压缩产物的本质

爸爸提的这条对：不该追「全局猜边率 10%」，该追「结论只建在确定边上」。
先拆构成（obsidian / dsh / aclos 前 40 个 `ipcMain` 文件）：

| 包 | 歧义定义数 | 结构性假名 | 占比 | 剩下的是什么 |
| --- | --- | --- | --- | --- |
| obsidian | 28 | 2（`get`、`constructor`） | 7% | `click`×16、`f`×3、`h`×2 |
| dsh | 208 | 19（`get`×11、`constructor`×4…） | 9% | `parse`×25、`check`×22、`processJSONSchema`×21 |
| aclos | 44 | 6（`constructor`×6） | 14% | `callback`×24、`ready_function`×2 |

**结构性假名只剩 7%–14%，而且都不是控制关键字**——是 `get`、`constructor` 这种
对象方法名，它们在 JS 里本来就是合法函数名，不能排除（`{ get() {} }` 是 getter，
是真函数）。

剩下的是真歧义，而且两类包表现不同：

- **压缩包（obsidian）**：`click`×16 这类 DOM 事件名，压缩产物到处挂；
- **未压缩包（dsh）**：`parse`、`check`、`processJSONSchema` 是不同模块里的同名工具函数，
  名字有意义、形态也相似。

dsh 那种如果模块表在，模块归属过滤能救；obsidian 单文件打包没有模块表，救不了。

## 所以阈值按包结构分层

| 包类型 | 判据 |
| --- | --- |
| 有 webpack 模块表 | 模块归属过滤后猜边率 **< 10%** |
| 单文件打包（无模块表） | **不设猜边率 KPI**。假名字清零后，真歧义率写进报告，图口径只报确定边支撑的结论 |
| 未压缩、模块边界清楚 | 作用域可见性补完后 **< 5%** |

**主链路切换的判据也改**：不是「猜边率 <10%」，而是「确定边产出的结论经过人工核验后
准确率达标」。确定边只占 20% 也能切——20% 的确定结论 + 明确标注不确定的部分，
比 100% 覆盖但一半靠猜值钱。

## 一条不变量

控制关键字排除现在有了断言：`scripts/selfcheck.py::check_keyword_names_excluded`。
这个 bug 在词法层、语法树层、函数定义层各犯过一次，靠真包实测发现太慢。

断言内容：`if/for/while/switch` 不许出现在 `function_defs` 里，同时真实函数
（`realFn`）不许被误伤。自检从 120 项变成 122 项。

**还没做到的**：三层各用一份关键字集合，应该合成一份共享常量。现在是各层各自过滤，
断言只守着函数定义层——这是已知的债。
