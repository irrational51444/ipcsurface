# 为什么不做「全量函数摘要」和「CPG」——做得起、算不动

这两件事都不是「不会」，是「在这批包上是负优化」。数字在下面，谁都能重跑。

## 全量函数摘要：0.3 秒变 8.4 秒

思路很清楚：每个函数算一次副作用签名（第 i 个形参流到哪些危险调用、
传给别的函数第 j 个形参），跨文件时查表拼接，深度就不再是参数。

它已经实现了：`jssem.function_summaries` 会算签名，并在 `rounds` 轮内
迭代到不动点，四层调用链一次查表就能出来（有用例守着）。
`jssem.interproc_taint_via_summaries` 是查表版的遍历器。

**但主链路没用它。** obsidian 实测：

| 做法 | 通道数 | 耗时 |
| --- | --- | --- |
| 递归跟（原做法） | 5 | **0.3 秒** |
| 全量摘要 + 查表 | 5 | **8.4 秒** |

同样的结论，慢 28 倍。原因是摘要「勤奋」：它把**全文件每个函数**都算一遍签名，
而递归版是「懒惰」的——只算真正被 handler 调到的那个（这两个包上是 0～3 个）。

摘要只有在「函数被大量复用」时才回本。这批包里 handler 的调用链极短，
所以预计算全是白算。

### 那留下了什么

`interproc_taint` 加了一层**按函数体区间缓存**：同一个函数被二十个 handler
调到时，`flows_into_danger` 只跑一次。这是摘要的收益，但保持了懒惰。
结论不变（有用例对比缓存前后），耗时回到 0.3 秒。

摘要那套 API 留着，等真遇到「一个工具函数被几十条通道调用」的包再用——
那时候预计算才划算。

## CPG：前提是真正的 AST，现在没有

CPG（代码属性图）是方向没错：把语法、控制流、数据依赖编成一张图，
「深度」不再是参数，而是图查询的自然结果。

但它有个硬前提：**得先有 AST**。现在的分析器是手写 tokenizer——有 token 流、
有括号配平、有块作用域近似，但没有表达式树。在 token 流上「建 CPG」，
建出来的只会是一张边全靠猜的图，比现在的近似更糟。

要真的上 CPG，等于换掉解析层重写一遍。那是另一个量级的工程，
不是这一版能塞进去的东西。

## 哪些是现在能做的

按「能不能今天就落地、能不能用数字证明」排：

1. **按需切片**（还没做，最便宜）：硬结论通道放开深度，候选通道维持浅层。
   现在所有 handler 一视同仁，这确实浪费。
2. **上下文敏感**（还没做，中等）：现在同一函数被两个 handler 调用时，
   只要有一个是脏的就报——这正是 dsh 精确率 11% 的来源。
   做法是给调用点打上下文标签，摘要按标签分桶。
3. **选择性 LLM**（没做，且有冲突）：需要联网，破坏「零依赖单文件」这条底线。
   真要做只能是可选的 `--llm` 分支，且结果必须标成「LLM 判断」而不是「静态分析」。
