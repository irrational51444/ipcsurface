# Electron IPC 扫描：把「未判定」从报告里救回来

> 十二个真实 Electron 应用跑下来的一点记录。没有 0day，只有一个工具设计上的坑，
> 和一堆可以复现的数字。
>
> 全文只讨论**分析方法和报告语义**，不提供任何可直接利用的细节：不点名具体产品，
> 不附原始 asar，不列可利用通道。涉及的产品都是公开流通版本。

## 起因

我写了个静态扫 Electron 应用 IPC 能力的工具，两个引擎：

- **名字级**：字符串和 token 级匹配，零依赖，快，但跟着代码走不通；
- **语法树级**：tree-sitter 建树，跨文件跟 require，慢十倍。

一开始我挺满意：语法树那版报得更少、更准。直到有人问了一句：

> `if apis:` 这行的语义是什么？

它的意思是「这一条我没查到危险 API」。但在安全工具里，**「查无此项」不能被当成「安全」**。

问题在这儿：语法树那版最后一步是

```python
if apis:
    out[channel] = apis
```

只有查到危险 API 的通道才进结果。于是两种完全不同的情况在输出里长得一模一样：

- handler 我看完了，里面确实没有危险调用；
- handler 是 `handlers.save`，跨模块引用，我根本没解出来。

**两种情况都不出现。** 报告因此永远比真相干净。

## 改法：三态，没有第四种

```python
record(channel, handler)  # 内部记 status
# status ∈ {with_sink, no_sink, unresolved}
```

- `with_sink` —— handler 里连到了危险 API，带文件名和偏移；
- `no_sink` —— handler 走到末尾，这一层没连到；
- `unresolved` —— handler 没解出来，这一层到不了它。

第三类必须显式存在、单独计数。它既不算危险，也不算干净，它就是「我不知道」。

改完立刻打脸一个我一直挂在嘴边的说法：「语法树版报得少是因为它更保守」。
真实情况是它一直看得见全部通道，只是把没证据的那些在最后一步扔了。

## 十二个包的数字

本机能找到的 Electron 应用全跑了一遍，两边通道集合逐条对比。

| 应用 | 名字级 | 语法树 | 连到危险 API | 这一层没连到 | 未判定 |
|---|---|---|---|---|---|
| A | 47 | 47 | 22 | 25 | 0 |
| B | 41 | 41 | 4 | 37 | 0 |
| C | 286 | 283 | 7 | 276 | 0 |
| D | 1 | 1 | 0 | 1 | 0 |
| E | 23 | 13 | 0 | 13 | 0 |
| F | 24 | 23 | 0 | 23 | 0 |
| G | 5 | 3 | 0 | 3 | 0 |
| 另外五个 | 0 | 0 | 0 | 0 | 0 |

（A–G 都是流通版本公开的桌面应用，出于篇幅考虑不点名；数字可以按下面说的方法
自己在本地重跑。）

**没有一个包是「语法树看见了而名字级没看见」。**

反过来，「只有名字级」的那 22 条，逐条查过来源，三类：

### 一、二进制里的字符串

`cancel-to-update`、`openFolder`、`REPORT_STAT` 这类名字，名字级引擎会报，
语法树引擎不报。查下去发现它们躺在 `.node` 原生模块、`.exe`、`.dll` 的
资源段里——名字级把 asar 里**所有文件**当文本扫，连 exe 都扫。

二进制里出现一个字符串，不构成「这里注册了一条 IPC 通道」的证据。

**结论：名字级的通道数偏大，不是因为它看得多。**

### 二、渲染层调用点 vs 主进程注册点

名字级的口径是 `handler ∪ invoke` 的并集，两边都算；语法树只数 `ipcMain.*` 注册点。
所以「渲染层喊了但主进程没人接」的名字只出现在名字级。两个口径不同，不是漏。

### 三、事件名和编译产物噪音

`did-finish-load` / `did-attach-webview` 是 webContents 事件，不是 IPC 通道；
还混进去过一条 shell 命令串和一个字面量 `undefined`。

## 一个真实的漏报

主板厂商那个工具里：

```js
ipcMain.on("uwp", this.onUWPEvent);
...
e.prototype.onUWPEvent = function (ev) { ... }
```

ES5 原型写法。我原来只收 `class X { m() {} }`，`this.onUWPEvent` 解析不到方法体，
三条通道全被判 `unresolved`——覆盖率 0%。

补上原型方法收集、handler 是成员引用时先试着本地解析之后，三条全部追到，
`unresolved` → `no_sink`，覆盖率 0% → 100%。

**这个漏报是靠「未判定单独计数」暴露出来的。** 在三态之前，它根本不会出现在报告里。

## 另一个坑：通道名走常量表

```js
const DESKTOP_IPC = { fileSave: "app-desktop:file-save" };
ipcMain.handle(DESKTOP_IPC.fileSave, ...)
```

只取属性名会得到 `fileSave`，而真实通道是 `app-desktop:file-save`。
两个引擎读的根本不是同一个字符串，通道集合永远对不上。

TypeScript 编出来的 enum 也是同一个坑：

```js
IPCChannel["RENDERER_START"] = "sentry-electron.renderer-start";
ipcMain.on(ipc.IPCChannel.RENDERER_START, ...)
```

`OBJ["KEY"] = "真值"` 这种赋值形态要认；常量表还得跨文件共享（定义在 types 里、
注册在另一个文件里）；`ipc.IPCChannel.X` 这种命名空间导入要试最后一段。

看证据档位：`literal`（调用点写的就是字符串）> `const-table`（查表还原）>
`heuristic`（查不到表，只能拿属性名顶上，**会错**，报告里明说「通道名是猜的」）。

修完十二个包上 `heuristic` 是 0 条。

## 两个静态引擎不能互相作证

这一点我一开始想错了，差点写进报告当卖点。

名字级和语法树**共享**：

1. 同一个 tokenizer——它认不出的东西两路都认不出；
2. 同一张危险 API 名单——名单里没有的，两路都不报；
3. 同一批静态盲区——动态注册、运行时拼名、加密 payload、`eval` 里的代码，两路都看不见。

它们高度相关。静态对静态 = 同一双眼睛看两遍，第二遍不带来独立信息。

「双重确认」成立的前提是两路独立。真要谈不漏，第二个传感器只能是**运行时探针**：
在 `ipcMain` 上读注册名，不碰源码。

这一条我没做到，工具里只有静态两路 + 一个靶场上的探针对齐。写在局限里。

## 措辞上的两条线

1. **「这一层没连到」不许写成「没有」**。状态列只能说
   `handler 连到危险 API` / `handler 里没连到` / `未判定`。
   连到只说明 handler 里走到了那些调用；没连到只说明这一层没看见。
   参数可不可控、上游拦没拦，这一层都不判。
2. **覆盖率要拆成两个数**：handler 率（走完的 handler / 认出来的通道）
   和文件率（真解析的 js / js 总数）。只看前者会虚高——文件根本没解析，
   它的通道压根不进分母。

## 怎么自己验一遍

上面每个结论都能在本地重跑，不需要信我。

### 1. 把 asar 拿出来

已安装的 Electron 应用，主进程代码基本都在：

```
<安装目录>\resources\app.asar
```

少数应用会把真正的入口藏在第二个 asar 里（比如 `resources/obsidian.asar`），
`app.asar` 只是个加载器——这种情况要看 `app.asar` 里的 `package.json`
和 `main.js` 指向哪。

格式：8 字节头（`<I` 版本 + `<I` 头长度）后面跟 JSON 目录，再往后是文件内容。

### 2. 两路各跑一遍

```
# 名字级
python ipcsurface.py app.asar --engine coarse -o coarse.md

# 语法树级
python ipcsurface.py app.asar --engine precise -o precise.md
```

输出里有两节直接能对：

- `## 通道` —— 名字级和工作区侧各列一栏；
- `## 每个通道的证据` —— 语法树那层的逐条判决。

### 3. 对不上的那几条，逐条查来源

这一步是全文最要紧的。别只看数字差，去查那些「只有名字级」的通道
**出现在哪个文件、什么上下文**：

```
grep -rl --binary-files=text 'cancel-to-update' <解包目录>
```

如果命中的是 `.node` / `.exe` / `.dll`，那就是二进制资源段里的字符串，
不是注册点——名字级把整个 asar 当文本扫，所以会收进来。

如果命中的是 `pages/xxx/index.js` 这种渲染层文件，去看是 `ipcRenderer.invoke`
还是 `ipcMain.handle`。前者是调用点，后者才是注册点。

### 4. 判断一条 `no_sink` 是真没连到，还是我漏了

去看它给的偏移：

```
`lib/main.js` @ 55958
```

用 `dd` 或者任何能按字节切的工具取那一段，人工读一遍 handler。
如果 handler 里明明白白有 `writeFileSync` 而报告说没连到，那就是我漏了——
这一类样本最值钱，麻烦贴出来。

### 5. 反过来的验证更便宜

拿一个你自己写的、确定有危险通道的小 Electron 程序跑一遍。
两路都该报出来；如果有哪一路报不出来，那条路径就没被覆盖到。

## 结论先行

如果你只想记一句话：

> **「没查到」和「查不到」不是同一件事。**
> 把前者写进报告的「没有任何问题」一栏，就是安全工具最坏的一种错。

其余都是这句话的推论：三态、覆盖率拆两个数、状态列不许写「安全」、
两个静态口径不许互相作证。

## 还欠着的

- **运行时探针没接成第二路**。CI 里那个只在靶场上跑，真包静态报 0 时不会触发提醒。
- **`unresolved` 在十二个包上实际只出现过一次**（就是上面那个 ES5 原型的例子）。
  机制有了，但真包上触发得少——这不代表它没用，代表大部分 handler 是内联箭头函数。
- **只有 Windows 侧的样本**，macOS / Linux 没跑。
- 五个 0 通道的包，**没有证明**它们真的没有通道。只能说这两条路都没走到。

上面所有数字都是在自己机器上跑出来的，方法照第二节那样复现即可。
需要看具体某个包的输出，可以私下交流——帖子里不点名，也不贴能直接对上的原始输出。
