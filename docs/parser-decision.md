# 解析器选型：手写、tree-sitter，还是换一条路

这份文档回答一个问题：**0.82.0 里那个手写解析器（`jsast.py`）该不该继续养下去。**
写它不是为了把决定说得漂亮，是为了把「我知道这是技术债」这件事留成证据。

结论先放这儿：**继续手写，但给它划死边界、上指标、上兜底。** 理由和代价都在下面，
不同意可以从「三条路线」那一节直接看数据。

## 为什么现在就要评

0.82.0 换成语法树之后，DeepSeek Harness 那个包从 39 条降到 3 条——降的是假阳性，
不是漏报。效果是实的，但代价也是实的：

- 0.81.0 出过「引号落单 / 字符串跨行 → 词法器抛错 → Obsidian 整份包算不出汇点」；
- 写这份文档的当天，为了拿真包数据又撞了两次同类事故：
  - DeepSeek Harness 某个文件里有 `…`（U+2026），词法器直接抛
    `没见过的字符`，整个文件连坐；
  - 抖音的一个文件里有没闭合的模板串，抛 `模板串没有结尾`，同样连坐。

也就是说：**手写解析器的失败模式是「整份放弃」，不是「少认一点」。**
这一条比语法覆盖不全更危险，因为它把「没看见」变成「没有」。上面三处现在都改成
宽容处理（认不出当标点跳过、没闭合就在那儿断开，并记进统计），但这类边角
会一直冒出来——所以要有一个明确的评估，而不是打一个补一个。

## 三条路线

| | 路线 A：继续手写（现状） | 路线 B：tree-sitter + 官方 JS grammar | 路线 C：换成成熟 JS 解析器的 Python 绑定（esprima / pyjsparser 一类） |
| --- | --- | --- | --- |
| 语法覆盖 | 只覆盖我写过的子集；实测未知节点 4.4%–6.5% | 官方 grammar，JS/TS 全覆盖，压缩产物也认 | 覆盖较全，但对近年语法（`?.`、`??`、类字段）常落后 |
| 真包实测速度 | **0.6–1.6 MB/s**（Python 单线程，见下表） | C 实现，通常快一到两个数量级 | 纯 Python，通常比手写还慢 |
| 依赖代价 | **零依赖**（卖点之一） | 要带 C 扩展（`tree_sitter` + `tree_sitter_javascript`），Windows 得有预编译轮子 | 纯 Python 依赖，轻，但仍是依赖；包大小和维护活跃度要跟 |
| 出错时的表现 | 我能让它「不炸但少认」，代价是隐性漏 | 语法错误会返回 ERROR 节点，位置明确 | 抛异常，得在外面兜 |
| 可维护性 | 我改得动：一个文件、无外部约束、AI 能整段重写 | 改不动：要跟 grammar 版本、binding 版本、打包轮子 | 中等：要跟上游版本，遇 bug 只能等 |
| 与项目定位的冲突 | 无 | 直接破坏 README 里「纯标准库、零依赖」这条 | 破坏同一条，但程度轻 |

### 手写路线的实测数据（2026-11-10，同一台机器）

**按包给数，不给平均。** 全局平均会把某个包的灾难盖掉，所以这里一包一行，
每行都写清扫了多少、哪些东西没认出来（`python scripts/ast_coverage.py` 可重测）：

| 包 | 扫了多少（封顶规则见下） | 未知节点率 | 建树吞吐 | 未知节点最集中的三类记号 |
| --- | --- | --- | --- | --- |
| Obsidian | 29 个文件 / 14.3 MB | **5.39%** | 0.9 MB/s | `,` 59,262 · `)` 16,678 · `:` 14,909 |
| DeepSeek Harness | 59 个文件 / 47.1 MB（封顶） | **5.57%** | 1.5 MB/s | `,` 106,778 · `:` 39,288 · `)` 26,735 |
| 抖音桌面端 | 60 个文件 / 7.4 MB（封顶） | **8.34%** | 0.7 MB/s | `,` 50,617 · `)` 15,972 · `:` 15,743（另有 15,571 个 `\x00`） |
| bilibili 桌面端 | 60 个文件 / 18.5 MB（封顶） | **5.76%** | 0.8 MB/s | `,` 112,426 · `)` 32,064 · `:` 16,977 |

封顶规则：最多 60 个最大的 `.js`、总字节不超过 48 MB（DeepSeek Harness 那种 200 MB 的包
全扫跑不完）。**扫的是子集，所以这些数字是「这部分代码的未知率」，不是「整包」**——
这条限制比数字本身更重要。

**归因（比数字有用）**：四包的前三名全是 `,` `)` `:` 这类收尾标点，不是 JSX、不是装饰器。
意思是：漏的地方集中在「某个构造的结尾没对齐」——对象/数组字面量的收尾、参数表边界、
三元与冒号的歧义。这一类是**解析器自己在某个形状上脱轨**，不是「这个语法没写」。
抖音那包另有 22,926 个 `\x00` 和 15 处未闭合模板：那不是语法问题，是**数据本身被截断或加密**，
任何解析器都读不出语义。所以抖音 8.34% 里有一部分根本不该算在「语法覆盖」头上。

**下一次看哪**：抖音是四包里最高（8.34%），它就是下一个要拆的样本——
拆完再决定是补解析器，还是承认那部分数据不可解析。

### 抖音那一包的未知节点，按三种原因拆开（2026-11-10）

「8.34%」把三件不同的事混成一件。用 `python scripts/unknown_breakdown.py` 拆开看：

| 分栏 | 是什么 | 计数 | 占全节点 |
| --- | --- | --- | --- |
| 语法未知 | 这门语法我没实现：`@` 装饰器、`#` 私有字段、JSX 的 `>`、正则里的转义 | 8,885 | 0.53% |
| **解析器脱轨** | 逗号、右括号、冒号这类**收尾标点**变成了未知节点——是我在某类构造上跑偏 | **95,630** | **5.69%** |
| 数据问题 | 控制字符、`\x00`、未闭合模板：文件本身被截断或加密，任何解析器都读不出语义 | 35,651 | 2.12% |

**扣掉数据问题后的「语法未知率」= 6.22%**（语法 0.53% + 脱轨 5.69%，分母仍是全部节点）。

样例（压缩产物是一整行，所以必须给列号 + 上下文才定位得到）：

- 语法未知：`pages/player/index.720d2ebe7aef88f0.js:2:100193` 记号 `/`，上下文
  `…){g.send()},0),g}if(/^data:([\w+-]+\/[\w…` —— 正则字面量被当成了除号；
- 解析器脱轨：`pages/player/index.720d2ebe7aef88f0.js:2:90737` 记号 `,`，上下文
  `….concat(t[4],") {")),t[2]&&(n+="@media "…` —— 一串 `concat(…)` 里收尾没对齐，
  后面整段跟着错位；
- 数据问题：`node_modules/mp4box/dist/mp4box.all.js:61:2497` 记号 `\x1a`，上下文 `…"",);PNG` ——
  这文件里嵌着二进制片段，不是语法问题。

**结论（也是下一步）**：真正的债不在「语法没写全」（0.53%），而在**解析器脱轨（5.69%）**，
根因集中在两处：正则字面量的判定（`if(/^data:…/)` 被当除号，`\/` 泄漏成未知记号），
以及 `concat(…)+"…"` 这类长表达式链的收尾对齐。这两处是真 bug，不是边界——
下一个版本先修它们，修完这一栏应该明显下降。

### 三个吞吐口径，别混着读

「0.6–1.6 MB/s」只是**建树**这一步的速度，不是工具的速度。真实工作流是三段：

| 阶段 | 做什么 | 吞吐 | 448 MB 样本上实际耗时 |
| --- | --- | --- | --- |
| 粗扫（默认） | 读 asar、抽通道名、名字级能力面 | ≈ 10 MB/s | **45.2 秒**（实测，含产出 JSON） |
| 语法树精查 | 只对可疑文件建树（每包封顶 12 个最大的 `.js`） | 0.6–1.5 MB/s | 取决于可疑文件总量：Obsidian 全流程 **3.6 秒** |
| 假想：全量建树 | 448 MB 每个 `.js` 都建树 | 0.6–1.5 MB/s | **约 300–750 秒**（不是现在的行为） |

所以「秒级」和「0.6 MB/s」不矛盾：日常跑的是第一段，第二段只碰少数文件，
第三段是没人会去跑的假想值——把它写在这张表里，是为了别再被误读成「工具很慢」。

### tree-sitter 在本机的可用性

`python -c "import tree_sitter"` → ModuleNotFoundError。要用就得装 C 扩展，
而本项目的定位是「纯标准库、把 asar 解出来就能跑」。所以路线 B 不是「性能更好就该选」，
它是**用项目定位去换覆盖率**。

## 决定：继续手写，但把代价显式化

选 A，不是因为 A 更好，是因为 B/C 会把「零依赖」这个前提换掉，而这是使用者的入口条件。
但这个选择要付代价，代价必须写在明处，而不是出事才知道：

1. **失败模式改成「软失败」**：认不出的字符、没闭合的字符串/模板/注释，一律跳过并计数，
   绝不抛异常让整份包作废。已实现（`jsparse.tokenize_with_stats`）。
2. **覆盖率变成可查看的数字**：`scripts/ast_coverage.py` 能对任何包输出未知节点率、
   吞吐、节点结构量。数字上去就是债在涨。
3. **边界写成表**（见 `docs/known-wrong.md` 的「解析器语法边界」一节），
   支持什么、不支持什么，一条条列，不许含糊。
4. **兜底不掉**：`channel_sinks`（名字级粗扫）保留。树口径挂了还有粗扫，
   两列都写「没连到」，绝不写成「没有」。

### 什么情况下会翻案

- **任一包**的未知节点率持续高于 10%（不是全局平均——平均会把某个包的灾难摊平）；
- 或者全局未知率连续三个版本上升；
- 或者需要在浏览器端、无 Python 环境里跑：那时零依赖反而是负担；
- 或者出现**第二次「整份放弃」级别的事故**（已改软失败，理论上不该再发生）。
  再发生就说明软失败这条路也堵不住，得换 B。

真到那一步，迁移成本是可控的：`jsast.py` 对外只暴露 `parse()` 和几个
`reachable_*` 函数，换成 tree-sitter 的节点遍历，上层调用不用动。
