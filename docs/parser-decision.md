# 解析器选型：手写、tree-sitter，还是换一条路

这份文档回答一个问题：**0.82.0 里那个手写解析器（`jsast.py`）该不该继续养下去。**
写它不是为了把决定说得漂亮，是为了把「我知道这是技术债」这件事留成证据。

结论先放这儿：**继续手写，但给它划死边界、上指标、上兜底。** 理由和代价都在下面，
不同意可以从「三条路线」那一节直接看数据。

## 为什么现在就要评

0.82.0 换成语法树之后，DeepSeek Harness 那个包从 39 条降到 3 条——降的是假阳性，
不是漏报。效果是实的，但代价也是实的：

- 0.81.0 出过「引号落单 / 字符串跨行 → 词法器抛错 → Obsidian 整份包算不出汇点」；
- 写这份文档的当天，为了拿真包数据又撞了两次同类事故：
  - DeepSeek Harness 某个文件里有 `…`（U+2026），词法器直接抛
    `没见过的字符`，整个文件连坐；
  - 抖音的一个文件里有没闭合的模板串，抛 `模板串没有结尾`，同样连坐。

也就是说：**手写解析器的失败模式是「整份放弃」，不是「少认一点」。**
这一条比语法覆盖不全更危险，因为它把「没看见」变成「没有」。上面三处现在都改成
宽容处理（认不出当标点跳过、没闭合就在那儿断开，并记进统计），但这类边角
会一直冒出来——所以要有一个明确的评估，而不是打一个补一个。

## 三条路线

| | 路线 A：继续手写（现状） | 路线 B：tree-sitter + 官方 JS grammar | 路线 C：换成成熟 JS 解析器的 Python 绑定（esprima / pyjsparser 一类） |
| --- | --- | --- | --- |
| 语法覆盖 | 只覆盖我写过的子集；实测未知节点 4.4%–6.5% | 官方 grammar，JS/TS 全覆盖，压缩产物也认 | 覆盖较全，但对近年语法（`?.`、`??`、类字段）常落后 |
| 真包实测速度 | **0.6–1.6 MB/s**（Python 单线程，见下表） | C 实现，通常快一到两个数量级 | 纯 Python，通常比手写还慢 |
| 依赖代价 | **零依赖**（卖点之一） | 要带 C 扩展（`tree_sitter` + `tree_sitter_javascript`），Windows 得有预编译轮子 | 纯 Python 依赖，轻，但仍是依赖；包大小和维护活跃度要跟 |
| 出错时的表现 | 我能让它「不炸但少认」，代价是隐性漏 | 语法错误会返回 ERROR 节点，位置明确 | 抛异常，得在外面兜 |
| 可维护性 | 我改得动：一个文件、无外部约束、AI 能整段重写 | 改不动：要跟 grammar 版本、binding 版本、打包轮子 | 中等：要跟上游版本，遇 bug 只能等 |
| 与项目定位的冲突 | 无 | 直接破坏 README 里「纯标准库、零依赖」这条 | 破坏同一条，但程度轻 |

### 手写路线的实测数据（2026-11-10，同一台机器）

取每个包里最大的 6 个 `.js`，跑 `python scripts/ast_coverage.py`：

| 包 | 最大 6 个文件合计 | 耗时 | 吞吐 | 未知节点率 | 函数 / 调用 / 成员访问 |
| --- | --- | --- | --- | --- | --- |
| Obsidian | 9,926 KB | 11.05 s | 0.9 MB/s | 6.11% | 16,693 / 78,554 / 140,879 |
| DeepSeek Harness | 26,165 KB | 15.87 s | 1.6 MB/s | 4.36% | 15,459 / 95,339 / 157,485 |
| 抖音桌面端 | 2,824 KB | 4.38 s | 0.6 MB/s | 6.47% | 12,663 / 39,173 / 59,095 |

「未知节点率」= 解析时认不出、只能跳过的地方占总节点数的比例。它不等于错误率——
有些是装饰器、私有字段、稀奇字面量这类对本题无关的东西；但**它就是隐性漏报的那部分**。

### tree-sitter 在本机的可用性

`python -c "import tree_sitter"` → ModuleNotFoundError。要用就得装 C 扩展，
而本项目的定位是「纯标准库、把 asar 解出来就能跑」。所以路线 B 不是「性能更好就该选」，
它是**用项目定位去换覆盖率**。

## 决定：继续手写，但把代价显式化

选 A，不是因为 A 更好，是因为 B/C 会把「零依赖」这个前提换掉，而这是使用者的入口条件。
但这个选择要付代价，代价必须写在明处，而不是出事才知道：

1. **失败模式改成「软失败」**：认不出的字符、没闭合的字符串/模板/注释，一律跳过并计数，
   绝不抛异常让整份包作废。已实现（`jsparse.tokenize_with_stats`）。
2. **覆盖率变成可查看的数字**：`scripts/ast_coverage.py` 能对任何包输出未知节点率、
   吞吐、节点结构量。数字上去就是债在涨。
3. **边界写成表**（见 `docs/known-wrong.md` 的「解析器语法边界」一节），
   支持什么、不支持什么，一条条列，不许含糊。
4. **兜底不掉**：`channel_sinks`（名字级粗扫）保留。树口径挂了还有粗扫，
   两列都写「没连到」，绝不写成「没有」。

### 什么情况下会翻案

- 未知节点率在真实语料上**持续高于 10%**：说明手写的边界已经盖不住了；
- 或者需要在浏览器端、无 Python 环境里跑：那时零依赖反而是负担；
- 或者出现**第二次「整份放弃」级别的事故**（已改软失败，理论上不该再发生）。
  再发生就说明软失败这条路也堵不住，得换 B。

真到那一步，迁移成本是可控的：`jsast.py` 对外只暴露 `parse()` 和几个
`reachable_*` 函数，换成 tree-sitter 的节点遍历，上层调用不用动。
