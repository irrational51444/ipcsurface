# 基准测试（Benchmark）

路线图 P0-4 的落地：给「分析能力到底准不准」一个能复算的度量，而不是一句「靶场覆盖率 1.00」。

## 数据从哪来

`tests/golden/real_packages.json`。里面每条通道都有人工依据——读了源码、写下
「这条通道该碰哪些危险 API」「为什么这条是误报」「为什么这条是已知漏报」。
标注跟着版本维护，越晚存量越大，所以早做。

## 怎么跑

```
python scripts/benchmark.py
```

包不在本机就跳过（跳过是「没测」，不是 0 分也不是 100%）。

## 口径（写死了，别漂）

- **通道级**：一个通道「说对了」= 工具报出它、且它名下至少一条可达危险 API 对得上。
  - 精确率 = 说对的通道数 / 工具报出的通道数（扣已知误报）
  - 召回率 = 说对的通道数 / 人工核对过的通道数
- **API 级**：在人工核对的通道上，按「该通道该有的危险 API」逐个对。
  - 精确率 = 报对的 API 数 / 报出的 API 数
  - 召回率 = 报对的 API 数 / 该有的 API 数

## 当前数字（2026-11-11）

| 应用 | 通道 P | 通道 R | 已核通道 | API P | API R |
| --- | --- | --- | --- | --- | --- |
| Obsidian | 100% | 95% | 21 | 22% | 100% |
| DeepSeek Harness | 100% | 100% | 3 | 60% | 100% |
| 合计 | 100% | 96% | 24 | 24% | 100% |

## 这几个数字该怎么读（重要）

- **通道级 100% / 96% 是好消息**：工具基本不把通道认错、也不漏（漏的那 1 条是
  `register-cli` 的 `exec`，别名藏在逗号表达式里，已登记 known_miss）。
- **API 级精确率 24% 是坏消息，也是实话**：工具在一个通道上报出的「可达危险 API」
  远多于人工确认的那几条。根因不是乱报，是**共用函数被保守地跟进去**——`_()`/`ae()`
  存配置、`se()`/`ee()` 读配置，几十条通道共用，于是每条都被标上一整排文件读写。
  这叫「能碰到」，不叫「会滥用」，但按「该通道该有的 API」打分，精确率就难看。

API 级精确率低，不是因为工具坏了，是因为**人工只确认了「该有」的子集，没逐个标注
「不该有」**。要把它提到有意义，得补 API 级的误报标注（`real_packages.json` 里
`false_positive` 现在是通道粒度，要下沉到「某通道某 API」粒度），这是 P0-4 的下一步。

## 还差什么（诚实的清单）

- 应用数：现在 2 个真包（Obsidian、DeepSeek Harness）。路线图要 5-10 个、覆盖不同
  构建链（webpack / vite / electron-forge / electron-vite / 原生 / 游戏客户端）。
- API 级误报标注：把 `false_positive` 从通道粒度下沉到 API 粒度，API 精确率才有意义。
- 抖音 / bilibili 两个已在本机的包：它们大量动态注册（名字拼装、第三方库），
  静态能抓到的少，需要先跑运行时探针对齐再入标注。
