# 基准测试：拿人工标注的标准答案算精确率与召回率

`python scripts/benchmark.py`。数据源是 `tests/golden/real_packages.json`——
那里每条通道都有人工依据：读了源码，写了为什么对、为什么错。

## 口径（写死，别漂）

**通道级**

- 说对 = 工具报了这条通道，且它名下至少一条可达危险 API 和人工标注对得上；
- 精确率 = 说对的通道数 / **工具报出的全部通道数**（扣掉明确标注的误报）；
- 召回率 = 说对的通道数 / 人工核对过的通道数。

**API 级**：在人工核对过的通道上，按「该通道该有的危险 API」逐个对。

**分母是全部报出的通道，不是核对过的那几条。** 这一条故意保守：
一条通道没人核过、工具报了，它仍然进分母。所以这个精确率是**下限**，
真实值只会更高，不会更低。

## 两路口径合并，不是二选一

0.145.0 之前这里写的是 `channel_sinks_ast or channel_sinks`——ast 那层只要有一条
非空，名字级那批就整个被丢掉。抖音 / bilibili / vivo / ACLOS 四个包因此算出来
全是 0。那不是「工具没报」，是尺子把它们扔了。

现在两路并集：任何一路看见就算看见。

## 结果（2026-11-14，0.145.0）

| 应用 | 通道 P | 通道 R | 已核通道 | API P | API R |
| --- | --- | --- | --- | --- | --- |
| obsidian | 95% | 100% | 21 | 22% | 100% |
| dsh | 11% | 100% | 3 | 30% | 100% |
| douyin | 未标注 | — | 0 | — | — |
| bilibili | 未标注 | — | 0 | — | — |
| vivo | 未标注 | — | 0 | — | — |
| aclos | 未标注 | — | 0 | — | — |
| **合计** | **48%** | **100%** | 24 | 23% | 100% |

通道级：24/50 报对，24/24 召回。
API 级：28/124 报对，28/28 召回。

## 这几个数字怎么读

**召回率 100% 只说明「我核过的那 24 条全报出来了」**，不说明真实应用不漏。
样本是 24 条，不是全量。

**dsh 的 11% 不是退步。** 合并两路之后它报出的通道从 3 条涨到 9 条，
其中只有 3 条在人工标注里。剩下 6 条要么是没核过、要么是误报，我分不清——
所以它们进了分母，精确率跌到 11%。这是「还没核」的代价，不是工具的错。

**obsidian 的 22% API 精确率是老问题**：共用函数被保守跟进去，报出的 API 远多于
该通道真有的。硬档那 25 条是人工读过源码的，软档不用核也不用信。

**四个包没标注就跳过，不写 0%。** 「工具一条没报」和「我还没核」完全是两件事，
打成同一个 0% 是噪音。

## 下一步

按投入产出排：

1. 给抖音、bilibili 各建 10 条左右的人工标注——两个包写法差异大，
   能把「是不是只在 obsidian 上灵」这件事验掉；
2. 把 dsh 报出的 9 条通道逐条核一遍，看那 6 条是真是假；
3. API 级精确率低是因为「共用函数被保守跟进去」，要收窄得做函数级副作用分析，
   成本高，排在后面。
